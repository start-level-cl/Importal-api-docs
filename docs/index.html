Flujo de Registro de Usuario

Proceso completo para registrar un nuevo usuario en Importal: desde la solicitud inicial (con normalización de roles y carga de documentos), verificación por email y teléfono, hasta la aprobación administrativa.

1
Usuario POST /registration-requests registration-lambda 🌐 Público

El usuario envía sus datos básicos. Para el perfil "inversor" se requiere dirección de despacho, transportType (maritimo/aereo) y comprobante en base64. Para "cliente_antiguo" se requieren los mismos datos pero sin comprobante. Los tipos "cliente", "vendedor", "bedeguero" se normalizan en la lambda.

Ver body de ejemplo
{
  "email": "usuario@ejemplo.com",
  "name": "Juan Pérez",
  "rut": "12.345.678-9",
  "phone": "+56912345678",
  "password": "Password123!",
  "profileType": "inversor",
  "consentimiento": true,
  "housingType": "casa",
  "streetAndNumber": "Av. Ejemplo 123",
  "region": "Región Metropolitana",
  "comuna": "Providencia",
  "agency": "FlowEx",
  "transportType": [
    "aerea"
  ],
  "comprobante": "<base64>",
  "comprobanteFileName": "comprobante.pdf",
  "comprobanteContentType": "application/pdf"
}
← 201 Created — Solicitud guardada en DynamoDB con status: PENDING y OTP pendientes
2
Usuario POST /registration-requests/{email}/send-code registration-lambda 🌐 Público

Genera códigos OTP y los envía vía SQS a notificaciones. Al pasar channel: "both", se despachan códigos a email y teléfono simultáneamente.

Ver body de ejemplo
{
  "channel": "both"
}
← 200 OK — { message: "OTP generated", channels: ["email", "phone"] }
3
Usuario POST /registration-requests/{email}/verify registration-lambda 🌐 Público

El usuario valida cada canal ingresando el código OTP. Cuando ambos canales están validados, se marca is_verified = true en DynamoDB.

Ver body de ejemplo
{
  "code": "123456",
  "channel": "email"
}
← 200 OK — { is_email_verified: true, is_phone_verified: false, is_verified: false }
4
Usuario PUT /registration-requests/{email}/update-contact registration-lambda 🌐 Público

Si el correo o teléfono es incorrecto, se puede actualizar el contacto siempre que la solicitud esté PENDING.

Ver body de ejemplo
{
  "email": "nuevo_usuario@ejemplo.com",
  "phone": "+56987654321"
}
← 200 OK — Contacto actualizado exitosamente
5
Administrador POST /api/v1/registration-requests/{email}/approve backend 🔐 JWT

El administrador aprueba la solicitud. El backend valida el estado y OTPs, crea el usuario en Importal-auth, persiste el perfil y direcciones en PostgreSQL, y marca APPROVED en DynamoDB.

Ver body de ejemplo
{
  "reviewedBy": "Administrador",
  "role": "client",
  "notes": "Papeles al día"
}
← 201 Created — { request: { status: "APPROVED" }, user: { userId: "uuid" } }
6
Usuario POST /auth/api/v1/auth/login auth 🌐 Público

El usuario ahora puede iniciar sesión para obtener su par de tokens JWT (accessToken y refreshToken).

Ver body de ejemplo
{
  "email": "usuario@ejemplo.com",
  "password": "Password123!"
}
← 200 OK — { accessToken: "eyJ...", refreshToken: "eyJ..." }

Flujo de Registro — Perfil Bodeguero

Proceso simplificado para registrar un bodeguero. Solo requiere los campos base (sin dirección ni comprobante).

1
Usuario POST /registration-requests registration-lambda 🌐 Público

El bodeguero solo requiere los campos base. La bodega asignada es fija y la asigna automáticamente el sistema al aprobar.

Ver body de ejemplo
{
  "email": "bodeguero@ejemplo.com",
  "name": "Pedro Bodega",
  "rut": "12.345.678-9",
  "phone": "+56912345678",
  "password": "Password123!",
  "profileType": "bodeguero",
  "consentimiento": true
}
← 201 Created
2
Usuario POST /registration-requests/{email}/send-code registration-lambda 🌐 Público

Idéntico al flujo general.

Ver body de ejemplo
{
  "channel": "both"
}
← 200 OK
3
Usuario POST /registration-requests/{email}/verify registration-lambda 🌐 Público

Repetir para channel: email y channel: phone.

Ver body de ejemplo
{
  "code": "XXXXXX",
  "channel": "email"
}
← 200 OK — is_verified: true
4
Administrador POST /api/v1/registration-requests/{email}/approve backend 🔐 JWT

Al aprobar, el bodeguero recibe bodega_asignada = "Av. Porvenir 1285, Casa 98, Lampa" automáticamente.

Ver body de ejemplo
{
  "reviewedBy": "Admin",
  "role": "client"
}
← 201 Created

Flujo de Autenticación y Refresh de Token

Cómo autenticarse, validar el token y renovarlo cuando expira.

1
Cliente POST /auth/api/v1/auth/login auth 🌐 Público

Enviar credenciales. El accessToken expira en 1h; el refreshToken en 7d.

Ver body de ejemplo
{
  "email": "usuario@ejemplo.com",
  "password": "Password123!"
}
← 200 OK — { accessToken, refreshToken }
2
Cliente GET /auth/api/v1/auth/validate auth 🔐 JWT

Endpoint usado por el API Gateway para verificar JWT entrantes. Incluir header: Authorization: Bearer .

← 200 OK — { valid: true }
3
Cliente POST /auth/api/v1/auth/refresh auth 🌐 Público

Cuando el accessToken expira, usar el refreshToken para obtener un nuevo par de tokens sin re-autenticarse.

Ver body de ejemplo
{
  "refreshToken": "eyJ..."
}
← 200 OK — { accessToken, refreshToken }
4
Cliente POST /auth/api/v1/auth/logout auth 🔐 JWT

Invalida el refreshToken en servidor. El accessToken queda activo hasta que expira por TTL.

← 200 OK

Flujo de Pedido con Reserva y Confirmación de Stock

Gestión de ciclo de vida del pedido: el cliente reserva stock de inmediato al crear el pedido, el vendedor confirma y despacha, y se libera la reserva de stock si la orden es rechazada o cancelada.

1
Cliente GET /api/v1/cliente/productos backend 🔐 JWT

Obtiene los productos activos disponibles en el sistema con su stock real disponible.

← 200 OK — Listado de productos
2
Cliente POST /api/v1/cliente/pedidos backend 🔐 JWT

El cliente crea un pedido especificando producto, talla y cantidad. El backend reserva de inmediato la cantidad del stock del producto en la base de datos.

Ver body de ejemplo
{
  "productId": 12,
  "quantity": 5,
  "talla": "L",
  "cargaId": 4
}
← 201 Created — { orderId: 88, status: "PENDING" }
3
Vendedor GET /api/v1/vendedor/pedidos backend 🔐 JWT

El vendedor consulta su lista de pedidos pendientes para procesar su despacho.

← 200 OK — Array de pedidos
4
Vendedor POST /api/v1/vendedor/pedidos/{id}/confirmar backend 🔐 JWT

El vendedor confirma que tiene la mercadería lista. Esto consolida el descuento del stock reservado y pasa el pedido a CONFIRMED.

← 200 OK — { id: 88, status: "CONFIRMED" }
5
Vendedor PUT /api/v1/vendedor/pedidos/{id}/estado backend 🔐 JWT

Si por alguna razón el pedido se cancela o rechaza, el backend automáticamente revierte la reserva y devuelve el stock al catálogo del producto.

Ver body de ejemplo
{
  "status": "REJECTED"
}
← 200 OK — { status: "REJECTED" } y stock devuelto

Flujo de Facturación, Carga de Pagos y Moras

Ciclo financiero periódico de cobros: el administrador gatilla facturación, consulta la API mindicador para conversiones USD/CLP, gestiona moras con intereses, el cliente sube comprobante, y el administrador aprueba/rechaza.

1
Administrador POST /api/v1/admin/cobros/trigger backend 🔐 JWT

Procesa cobros acumulados, consulta tarifas de comisiones y logística, convierte valores de USD a CLP usando la API de mindicador, y a la vez identifica cobros OVERDUE para aplicar recargos por mora e intereses.

← 200 OK — { ok: true, message: "Procesamiento completado." }
2
Cliente GET /api/v1/cliente/cobros backend 🔐 JWT

El cliente ve el detalle de sus facturas vigentes, fechas de vencimiento y montos cobrados en CLP.

← 200 OK — Array de cobros pendientes
3
Cliente GET /api/v1/cliente/cobros/{id}/pdf backend 🔐 JWT

Descarga un archivo PDF firmado con el detalle e ítemes cobrados en el período.

← 200 OK — Archivo PDF en base64
4
Cliente POST /api/v1/cliente/cobros/{id}/pagar backend 🔐 JWT

El cliente realiza transferencia bancaria y sube el comprobante (formato PDF o imagen). El estado del cobro pasa a PENDING_REVIEW.

Ver body de ejemplo
[Archivo binario en Multipart/Form-Data]
← 200 OK — Comprobante en revisión
5
Administrador POST /api/v1/admin/cobros/{id}/confirmar backend 🔐 JWT

El administrador valida el comprobante contra su banco. Si está correcto, aprueba el cobro, pasando su estado a PAID y liberando los despachos asociados.

Ver body de ejemplo
{
  "approved": true,
  "admin_comment": "Comprobante verificado en cuenta corriente."
}
← 200 OK — Cobro marcado como PAID

Flujo de Logística: Solicitudes de Tránsito y Salida Anticipada

Proceso de despacho consolidado en cargas (aéreas o marítimas) por parte del vendedor, incluyendo aprobación de tránsito, cierres temporales, salida anticipada y reasignación de órdenes post-cierre.

1
Vendedor POST /api/v1/vendedor/solicitudes-carga backend 🔐 JWT

El vendedor informa que tiene mercadería lista para embarque (AEREA o MARITIMA) para que la administración del sistema le asigne transporte.

Ver body de ejemplo
{
  "tipo_carga": "AEREA"
}
← 201 Created — Solicitud de tránsito registrada
2
Administrador POST /api/v1/admin/solicitudes-carga/{id}/aprobar backend 🔐 JWT

El administrador revisa el volumen y tipo, aprueba la solicitud de tránsito, lo que la asocia a una Carga consolidadora oficial del sistema.

← 200 OK — Solicitud de tránsito aprobada
3
Vendedor POST /api/v1/vendedor/cargas/transicion-cierre backend 🔐 JWT

El vendedor puede forzar un despacho anticipado de su carga antes del cierre automático de la ventana temporal. El sistema reasigna automáticamente a la siguiente carga disponible los pedidos que quedaron fuera.

Ver body de ejemplo
{
  "tipo_carga": "AEREA"
}
← 200 OK — Transición de cierre procesada
4
Bodeguero PUT /api/v1/bodeguero/cargas/{id}/status backend 🔐 JWT

Al arribar la carga, el bodeguero actualiza su estado (por ejemplo, a ARRIVED o RECEIVED), gatillando notificaciones de seguimiento al cliente.

Ver body de ejemplo
{
  "status": "ARRIVED",
  "notes": "Llegada exitosa en bodega Santiago."
}
← 200 OK — Estado de carga actualizado
5
Bodeguero GET /api/v1/bodeguero/pedidos/{id}/auditoria backend 🔐 JWT

El bodeguero o administrador puede consultar la bitácora completa de cambios de estado y tracking del pedido para auditoría.

← 200 OK — Historial de transiciones de estado
