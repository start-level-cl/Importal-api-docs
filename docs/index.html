Flujo de Registro de Usuario

Proceso completo para registrar un nuevo usuario en Importal: desde la solicitud inicial hasta la aprobación y primer acceso.

1
Usuario POST /registration-requests registration-lambda 🌐 Público

El usuario envía sus datos básicos (email, nombre, RUT, teléfono, contraseña, profileType). Para inversores también se requiere comprobante PDF en base64, dirección de despacho y datos de sala/agencia.

Ver body de ejemplo
{
  "email": "usuario@ejemplo.com",
  "name": "Juan Pérez",
  "rut": "12.345.678-9",
  "phone": "+56912345678",
  "password": "Password123!",
  "profileType": "inversor",
  "consentimiento": true,
  "housingType": "casa",
  "streetAndNumber": "Av. Ejemplo 123",
  "region": "Región Metropolitana",
  "comuna": "Providencia",
  "agency": "FlowEx",
  "selectedSala": "aerea",
  "comprobante": "<base64>",
  "comprobanteFileName": "comprobante.pdf",
  "comprobanteContentType": "application/pdf"
}
← 201 Created — Solicitud guardada en DynamoDB con status: PENDING
2
Usuario POST /registration-requests/{email}/send-code registration-lambda 🌐 Público

Se solicita el envío de códigos OTP a ambos canales simultáneamente usando channel: "both". El sistema genera los códigos, los almacena en DynamoDB con TTL y los envía vía SQS al sistema de notificaciones.

Ver body de ejemplo
{
  "channel": "both"
}
← 200 OK — { "issuedCodes": [ {"channel": "email", "code": "123456"}, {"channel": "phone", "code": "654321"} ] }
3
Usuario POST /registration-requests/{email}/verify registration-lambda 🌐 Público

El usuario ingresa el código recibido por email. La lambda valida el OTP, lo marca como utilizado y actualiza is_email_verified = true en DynamoDB.

Ver body de ejemplo
{
  "code": "123456",
  "channel": "email"
}
← 200 OK — { is_email_verified: true, is_phone_verified: false, is_verified: false }
4
Usuario POST /registration-requests/{email}/verify registration-lambda 🌐 Público

El usuario ingresa el código recibido por SMS/llamada. Una vez verificados ambos canales, is_verified se vuelve true y la solicitud queda lista para aprobación administrativa.

Ver body de ejemplo
{
  "code": "654321",
  "channel": "phone"
}
← 200 OK — { is_email_verified: true, is_phone_verified: true, is_verified: true }
5
Administrador POST /api/v1/registration-requests/{email}/approve backend 🔐 JWT

Un administrador con JWT válido aprueba la solicitud. El backend valida el estado PENDING y is_verified, crea el usuario en Auth (Importal-auth), persiste el perfil en PostgreSQL, actualiza el estado a APPROVED en DynamoDB y envía email de bienvenida.

Ver body de ejemplo
{
  "reviewedBy": "Administrador",
  "role": "client"
}
← 201 Created — { request: { status: "APPROVED" }, user: { userId: "uuid", role: "client" } }
6
Usuario POST /auth/api/v1/auth/login auth 🌐 Público

El usuario puede ahora autenticarse con su email y contraseña. Recibirá un accessToken JWT y un refreshToken para acceder a los endpoints protegidos.

Ver body de ejemplo
{
  "email": "usuario@ejemplo.com",
  "password": "Password123!"
}
← 200 OK — { accessToken: "eyJ...", refreshToken: "eyJ..." }

Flujo de Registro — Perfil Bodeguero

Proceso simplificado para registrar un bodeguero. Solo requiere los campos base (sin dirección ni comprobante).

1
Usuario POST /registration-requests registration-lambda 🌐 Público

El bodeguero solo requiere los campos base. La bodega asignada es fija y la asigna automáticamente el sistema al aprobar.

Ver body de ejemplo
{
  "email": "bodeguero@ejemplo.com",
  "name": "Pedro Bodega",
  "rut": "12.345.678-9",
  "phone": "+56912345678",
  "password": "Password123!",
  "profileType": "bodeguero",
  "consentimiento": true
}
← 201 Created
2
Usuario POST /registration-requests/{email}/send-code registration-lambda 🌐 Público

Idéntico al flujo general.

Ver body de ejemplo
{
  "channel": "both"
}
← 200 OK
3
Usuario POST /registration-requests/{email}/verify registration-lambda 🌐 Público

Repetir para channel: email y channel: phone.

Ver body de ejemplo
{
  "code": "XXXXXX",
  "channel": "email"
}
← 200 OK — is_verified: true
4
Administrador POST /api/v1/registration-requests/{email}/approve backend 🔐 JWT

Al aprobar, el bodeguero recibe bodega_asignada = "Av. Porvenir 1285, Casa 98, Lampa" automáticamente.

Ver body de ejemplo
{
  "reviewedBy": "Admin",
  "role": "client"
}
← 201 Created

Flujo de Autenticación y Refresh de Token

Cómo autenticarse, validar el token y renovarlo cuando expira.

1
Cliente POST /auth/api/v1/auth/login auth 🌐 Público

Enviar credenciales. El accessToken expira en 1h; el refreshToken en 7d.

Ver body de ejemplo
{
  "email": "usuario@ejemplo.com",
  "password": "Password123!"
}
← 200 OK — { accessToken, refreshToken }
2
Cliente GET /auth/api/v1/auth/validate auth 🔐 JWT

Endpoint usado por el API Gateway para verificar JWT entrantes. Incluir header: Authorization: Bearer .

← 200 OK — { valid: true }
3
Cliente POST /auth/api/v1/auth/refresh auth 🌐 Público

Cuando el accessToken expira, usar el refreshToken para obtener un nuevo par de tokens sin re-autenticarse.

Ver body de ejemplo
{
  "refreshToken": "eyJ..."
}
← 200 OK — { accessToken, refreshToken }
4
Cliente POST /auth/api/v1/auth/logout auth 🔐 JWT

Invalida el refreshToken en servidor. El accessToken queda activo hasta que expira por TTL.

← 200 OK

Flujo de Pedido — Vista Cliente

Cómo un cliente navega el catálogo, realiza un pedido y gestiona el pago.

1
Cliente GET /api/v1/cliente/productos backend 🔐 JWT

Lista de productos disponibles para el cliente autenticado.

← 200 OK — ProductArray
2
Cliente POST /api/v1/cliente/pedidos backend 🔐 JWT

El cliente crea un pedido seleccionando un producto, cantidad y la carga a la que se asocia.

Ver body de ejemplo
{
  "productId": 1,
  "quantity": 2,
  "cargaId": 10
}
← 201 Created
3
Cliente POST /api/v1/cliente/pagos/transbank/iniciar backend 🔐 JWT

Inicia el flujo de pago Transbank. Retorna la URL de redirección y el token de transacción.

Ver body de ejemplo
{
  "cobro_id": 5,
  "amount_clp": 150000
}
← 201 Created — { url, token }
4
Cliente POST /api/v1/cliente/pagos/transbank/confirmar backend 🔐 JWT

Una vez redirigido de vuelta, el cliente confirma el pago con el token de Transbank.

Ver body de ejemplo
{
  "transaction_id": "TX123",
  "token": "abc..."
}
← 200 OK — Cobro confirmado
